## 3. 第 1 部: 429 の理由を読んで、扱いを分ける(`cloud_forecast.py`・`grid_cache.py`)

1. 429 のとき、本文の `reason` を読み、画面に出す。JSON として読めなければ、本文の先頭 200 文字を出す。
2. 種類を分ける: `minutely`・`hourly`・`daily`・`unknown`。`FetchOutcome` に入れて返す。
3. 扱い:
   - `minutely`: 65 秒待って、同じセルをもう一度取る。1 回の実行で合計 5 回まで。6 回目は今と同じ中止。待つ前に「1分の上限のため65秒待ちます(n/5)」と 1 行出す。
   - `hourly`・`daily`・`unknown`: 今と同じ中止(`OpenMeteoDailyLimitError`、終了コード 2)。中止の文に、種類と reason を入れる。
4. 例外の名前 `OpenMeteoDailyLimitError` はそのまま残す(呼び出し側を壊さない)。説明の文だけ直す。
5. ひまわり画像(`himawari_image.py`)の 429 は今のまま。

## 4. 第 2 部: 通信の間隔を抑える(`grid_cache.py` か `cloud_forecast.py`)

1. 1 回の通信の重さを見積もる: `max(1, 変数の数 / 10) × max(1, 予報日数 / 14)`。
2. 直近 60 秒の重さの合計が、上限(定数。初期値 **300** = 1 分の上限 600 の半分)を超えないように、通信の前に必要なだけ待つ。
3. キャッシュヒットは数えない。再試行の通信は数える。
4. 待った秒数の合計を `FetchSummary` に持たせ、`console_line()` の後ろに足す(0 秒のときも出してよい)。例: `… / 間隔の調整 212.0 秒`
5. 「実行時間の内訳」の行は、通信・間隔の調整・それ以外に分けて出す。
6. 時計と sleep は差し替えられる形にして、テストで確かめる(通信なし):
   上限を超えないこと、キャッシュヒットで待たないこと、重さの計算、待った秒数の集計。

見積もり: 617 回 × 約 2.5 = 約 1,540 回分。上限 300/分なら、通信全体で 5〜6 分になる。これは受け入れる。
