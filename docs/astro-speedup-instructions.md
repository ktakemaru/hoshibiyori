**本人は長時間 PC を操作できない。質問・確認・承認の依頼を一切せず、最後まで自分で進めること。**
迷ったら 2 章の決まりで自分で決め、決めた内容と理由を報告書に書く。

## 1. 目的と背景

- 前回の計測(`docs/open-meteo-session-report.md`): `explore_hoshibiyori.py --target stars`、897 地点、全体 2363.8 秒。
  通信は 182.9 秒(7.7%)、**通信以外が 2180.8 秒(92.3%)**。内訳は測っていない。
- 目的: 通信以外の時間の内訳を測り、**出力を 1 文字も変えずに**短くする。
- 目標の目安: 通信以外の時間を半分以下に。届かなくてもよい。届かなかった理由を報告書に書く。

## 2. 無人で進めるための決まり

### 2.1 止まらない

- 本人に質問しない。「どちらにしますか」「進めてよいですか」と書いて待たない。
- うまくいかない変更は取り消して(`git restore`)、報告書に書き、次へ進む。
- 迷ったら「変更が小さい側」「結果が変わらない側」「やらない側」を選ぶ。

### 2.2 してよい操作・しない操作

- 使うコマンドは `git`(ローカルの操作だけ)と `py` だけ。
- `git push`・`git fetch`・`git pull`・`gh` は使わない。main へ commit しない。タグを打たない。版を上げない。
- パッケージのインストール・更新をしない。新しいライブラリを足さない。
- WebFetch・WebSearch を使わない。ヤマビヨリのフォルダは開かない。
- 一時ファイル・ログ・計測用のキャッシュは、`CLAUDE.md` の「単発分析の入力の退避ルール」に従い、`C:\hoshibiyori-archive\astro-speedup-20261112\` に置く。それ以外のリポジトリの外には書かない。
- 今あるファイルを消さない。今ある雲量のキャッシュ(`cloud_cache`)は読まない・書かない・消さない。

### 2.3 始める前の確認

- `git status` と `git log -3 --oneline` を見る。main に「接続の使い回し」の変更が入っていること(`cloud_forecast.py` に `_http_session` があること)を確かめる。
  入っていなければ、今いるブランチの HEAD から作業ブランチを切り、報告書に書く(pull はしない)。
- 未 commit・未追跡のファイルがあっても捨てない・stash しない。commit には自分が変えたファイルだけを `git add <ファイル名>` で入れる。
- 作業ブランチは `feature/astro-speedup`(main から切る)。

### 2.4 通信の量と時間の上限

- Open-Meteo に通信する実行は **1 回だけ**(3 章の R0)。あとはすべて通信なし。
- 429 が出たら R0 をやめ、今ある `cloud_cache` を**写した**フォルダ(元は触らない)を固定キャッシュに使う。足りないセルは欠測のまま比べる。
- 1 回の実行が 60 分を超えたら止めて、報告書に書く。
- 作業全体は 7 時間を目安にする。超えそうなら、残りを「未着手」と書いて 7 章へ進む。

### 2.5 変えないもの

スコア・候補の選び方・順位・足切りの値・計算の式・サンプルの間隔(15 分)・探索の幅(48 時間)・精度・
画面の出力の文・レポート(HTML)の中身・取得の URL やパラメータ・キャッシュのキーと有効期限・429 の扱い。

### 2.6 テストと commit

- テストは `py -X utf8 -m unittest discover -s tests`。各 commit の前に全テストを通す。
- 変更 1 つごとに commit する。

## 3. 測り方

計測用のスクリプトを `scripts/measure_explore.py` として作る(利用者向けの既定の動きは変えない。commit する)。できること:

- 雲量のディスクキャッシュの置き場を、指定したフォルダに向けて `explore` を実行する。
- `--frozen`: そのフォルダのキャッシュを、有効期限を無視して読む(通信 0 回)。キャッシュに無いセルは通信せず欠測にする。
- `--primary-only`: 主要候補(146 件)だけで実行する(速い確かめ用)。
- `--profile`: `cProfile` をかけ、累積時間の上位 40 件をファイルに出す。
- 画面の出力をファイルに保存する。全体・通信・通信以外の秒数を JSON に保存する。

実行の種類:

| 名前 | 内容 | 通信 |
|---|---|---|
| R0 | 新しい空のフォルダで、全 897 地点を 1 回実行。このフォルダが「固定キャッシュ」になる | あり(1 回だけ) |
| 速い確かめ | 固定キャッシュ・`--frozen --primary-only` | なし |
| 全体の確かめ | 固定キャッシュ・`--frozen`・全 897 地点 | なし |

**出力が同じかの確かめ方**: 変更の前と後を、同じ固定キャッシュ・同じ種類の実行で比べる。
秒数・実行日時・API 呼び出しとキャッシュヒットの回数が入る行を除いて、1 文字も違わなければ「同じ」。除く行の決め方はスクリプトに書き、報告書にも書く。
`explore` は「今日」を基準に夜を選ぶので、**比べる 2 つは同じ日付(JST)の中で実行する**。日付が変わったら、変更前の側(main のコード)を取り直す。
変更前の出力は、main のコードを `git worktree` か `git stash` を使わない方法(例: `git show main:<ファイル>` で写した別フォルダ、または作業の最初に取っておく)で作る。

## 4. 段階 1: 内訳を測る(コードは変えない)

1. R0 を実行する。
2. 速い確かめを `--profile` つきで実行する。
3. 報告書に、累積時間の上位 20 件と、次のまとまりごとの秒数(全体に対する割合)を書く:
   薄明の時刻(`find_astro_dark_events`・`find_sun_events`)/月の位置のサンプル(`longest_negligible_window`)/
   対象の方角・高度のサンプル(`compute_target_window`)/雲量の集計(`get_level_cloud_forecast`・`hourly_sky_obstruction_and_cloud_sea`)/光害/地形/その他。
4. 同じ引数での呼び出しが何回繰り返されているかを数える(例: `compute_site_night_window` が同じ地点・同じ夜で何回呼ばれるか、同じ格子セルの雲量の時系列を何回 辞書に直しているか)。

## 5. 段階 2: 短くする(効果の大きい順に、1 つずつ)

行ってよい変更:

- **同じ入力の計算を繰り返さない**: 結果の使い回し(メモ化)。例: 地点 × 夜の薄明・無月時間帯、同じセルの時系列の変換、同じ緯度経度の `wgs84.latlon`。
- **ループの外へ出す**: 毎回作り直しているが中身が同じもの。
- **まとめて計算する**: Skyfield に時刻の配列を渡して、サンプルを 1 回で計算する。ただし出力が同じ場合に限る。
- 計算の順番を変えて、足切りで落ちる地点の重い計算を後回しにする。ただし出力(順位・表示・件数の行)が同じ場合に限る。

行わない変更(案として報告書に書くだけ):

- 式・精度・サンプルの間隔・探索の幅を変える
- 近い地点をまとめて近似する
- マルチプロセス・スレッドで同時に計算する
- 計算結果をディスクに保存して、次の実行で使う

進め方:

1. 変更を 1 つ入れる。
2. 全テストを通す。
3. 速い確かめで、出力が同じこと・時間が減ったことを見る。
4. 同じでなければ取り消す。効果が通信以外の時間の 3% 未満なら取り消す。
5. 残す変更は commit する(commit の文に、速い確かめの前後の秒数を書く)。
6. 効果のありそうな候補がなくなるか、時間の目安に近づくまで繰り返す。

足すテスト(通信なし): メモ化したものが、同じ引数で同じ値を返すこと。違う地点・違う夜で値が混ざらないこと。

## 6. 段階 3: 全体の確かめ

1. 同じ日付の中で、変更前(main のコード)と変更後を、全体の確かめで 1 回ずつ実行する。
2. 出力が同じことを確かめる。違ったら、違いの出た変更を 1 つずつ戻して突き止め、取り消す。
3. 全体・通信以外の秒数の前後を記録する。
4. 余裕があれば、`generate_report.py` も固定キャッシュで前後を比べる(天気図・ひまわりなど通信が要る部分は実行しない。分けて実行できなければ、やらずに報告書に書く)。

## 7. 文書と報告書

- `CHANGELOG.md` の `[Unreleased]` の `### Changed` に、何を速くしたかと実測の秒数を書く。
- `CLAUDE.md` の「今後の課題」にある実行時間の項に、今回の結果を追記する。
- 報告書 `docs/astro-speedup-report.md`。冒頭に、1 分で読める要約を置く。中身:
  1. 表: 変更前・変更後の、全体/通信以外の秒数(速い確かめ・全体の確かめ)
  2. 段階 1 の内訳(上位 20 件、まとまりごとの秒数、繰り返しの回数)
  3. 入れた変更の一覧(それぞれの効果と、出力が同じだったこと)
  4. 取り消した変更と理由
  5. 行わなかった案(効果の見込みと、結果が変わるおそれ)
  6. 自分で決めたことの一覧
  7. 言えること・言えないこと
  8. 本人が行う push と PR の手順(ウィンドウの名前つきで 1 ステップずつ)
- この指示書も一緒に commit する。

## 8. 終わりの条件

- 全テストが通っている。自分が変えたファイルに未 commit のものがない。push はしていない。
- 最後の返事は、報告書の要約と場所だけにする。質問で終わらない。
